전사사업관리시스템

전달받은 요구사항대로 확장한 구조를 다시 걷어낸 경험

상황 비용은 계약 단계에서만 청구할 수 있어 계약번호로 연결해 관리했습니다. 이후 제안 단계에서도 비용이 발생할 수 있다는 요청을 받아 구조를 확장했지만, 현업은 결국 계약 단계만 사용해 확장한 기능을 모두 회수했습니다. 원인 제안과 계약은 서로 다른 테이블이라 번호가 각자 고유합니다. 이를 한 컬럼으로 연결하려고 제안·계약 구분 컬럼을 추가했고, 등록·조회·관리 기능마다 분기 처리가 퍼졌습니다. 요청이 실제 업무 방식과 맞는지 현업에 직접 확인하지 않은 채 진행한 것이 근본 원인이었습니다. 해결 구분 컬럼과 분기 로직을 걷어내고 계약 기준 구조로 되돌렸습니다. 운영 반영 전 개발 DB 단계였기 때문에, 추가했던 데이터는 삭제해 정리했습니다. 이후 구조가 바뀌는 요청은 현업에 업무 프로세스를 다시 설명하고, 맞는지 확인받은 뒤 진행하고 있습니다. 알게 된 점 DB 구조를 바꾸는 요청일수록 전달받은 내용만으로 진행하면 되돌리는 비용이 커진다는 걸 배웠습니다. 무엇을 만들지 먼저 맞추는 것이 재작업을 줄이는 가장 빠른 방법이었습니다.
감사정보시스템

대용량 연계 파일 적재 중 메모리 부족(OOM) 발생

상황 외부 시스템과 연계하는 배치가 연계 파일을 DB에 적재하던 중, Heap 메모리가 부족해 OutOfMemoryError가 발생하고 서버가 강제로 중단됐습니다. 원인 배치가 연계 파일의 데이터를 한 번에 전부 읽어 목록(List)에 담은 뒤 INSERT하는 구조였습니다. 파일이 커지자 모든 행이 Heap 메모리에 한꺼번에 올라가 부하가 걸렸습니다. 해결 파일을 한 줄씩 읽는 즉시 INSERT하도록 바꿔 목록에 쌓지 않게 했습니다. 처리가 끝난 행은 바로 GC 대상이 되어, 파일 크기와 관계없이 메모리 사용량이 일정해졌습니다. 파일마다 처리 결과와 적재 건수를 연계 이력 테이블에 기록해, 어떤 파일이 몇 건 들어갔는지 확인할 수 있게 했습니다. 알게 된 점 양이 늘어날 수 있는 데이터는 모두 모아서 한 번에 처리하기보다, 읽는 대로 흘려보내는 방식이 안전하다는 걸 배웠습니다. 1만 건 단위로 진행 로그를 남겨 장애가 나도 어디까지 적재됐는지 확인할 수 있게 했습니다.
감사정보시스템

알림 API 요청이 TLS 1.1로 전송돼 수신 실패

상황 알림 API로 보낸 메시지가 수신되지 않았고, 서버 로그에는 API 전송 실패가 기록됐습니다. 원인 API를 받는 서버에 확인해 보니 TLS 1.2 이상만 허용하고 있었습니다. 그런데 운영 서버의 Java가 HTTPS 요청을 TLS 1.1로 보내고 있어, 연결 단계에서 거부되고 있었습니다. 해결 요청 전에 SSLContext를 TLS 1.2로 생성해 HTTPS 연결에 적용했고, 이후 정상적으로 수신되는 것을 확인했습니다. 알게 된 점 코드에 문제가 없어도 실행 환경(JDK의 기본 TLS 버전) 때문에 연동이 실패할 수 있다는 걸 배웠습니다. 기본 소켓 설정을 바꾸는 방식은 같은 서버의 다른 HTTPS 연동에도 영향을 주기 때문에, 연결 단위로 지정하는 편이 더 안전하다는 점도 알게 됐습니다.
감사정보시스템

암묵적 형변환에 기대던 쿼리가 잘못된 입력 한 건에 메뉴 접근 불가

상황 잘 동작하던 외부강의·회의 신고 메뉴가 갑자기 ORA-01861 오류로 열리지 않았습니다. 원인 휴일 테이블의 날짜는 문자열(VARCHAR2)로 저장되는데, 조회 쿼리가 형식 지정 없이 DATE 값과 BETWEEN으로 비교해 Oracle의 암묵적 형변환에 의존하고 있었습니다. 평소에는 문제가 없었지만, 형식에 맞지 않는 휴일 데이터가 한 건 입력되자 변환에 실패하며 숨어 있던 약점이 드러났습니다. 해결 같은 비교를 쓰는 조회·목록·엑셀 쿼리 3곳을 찾아 TO_DATE(RESTDE_DE, 'YYYYMMDD')로 형식을 명시했습니다. 알게 된 점 지금 잘 돌아간다는 것이 안전하다는 뜻은 아니라는 걸 배웠습니다. 타입이 다른 값을 비교할 때는 DB 설정이나 데이터 상태에 기대지 말고 형식을 명시해야 합니다. 다만 이번 조치는 조회 쪽만 보완한 것이라, 잘못된 값이 다시 들어오지 않도록 휴일 등록 단계에서 형식을 검증하는 것이 근본적인 해결이라고 생각합니다.
