만들기 전에 왜 필요한지 먼저 묻고, 현업과 함께 방법을 고르는 개발자

첫 프로젝트였던 전사경영관리시스템을 개발하며, 잘 만드는 것보다 무엇을 만들어야 하는지 정확히 아는 것이 먼저라는 걸 배웠습니다. 직접 구현한 기능의 사용자 문의와 오류 대응을 맡으면서는 사용자와의 소통이 기능만큼 중요하다는 것도 알게 됐습니다. 지금은 내부회계관리·상시모니터링·감사정보 시스템의 고객 CS를 맡으며 유지보수와 기능 개선을 하고 있습니다.

전사경영시스템

개발
IPS · 2025.08 – 2026.03 · 팀원 4명 중 1명

전사 단위 경영 업무를 다루는 사내 시스템의 신규 개발에 참여해, 비용관리 메뉴를 맡았습니다.

기여한 부분
  • 담당 모듈 — 법인카드 관리, 비용 관리(PC·모바일), 경비 결재
  • 핵심 프로세스 — 법인카드 사용내역 자동 수집 → 프로젝트·계정 지정 → 그룹웨어 결재 상신 → 결재 결과 반영 → 최종 결재 완료 건 집계
  • 시스템 연동 — 법인카드 사용내역은 DB 프로시저로 DB to DB 연동해 IPS에 자동 반영하고, 그룹웨어 결재 결과(반려·완료·취소)는 Quartz 배치로 동기화
사용 기술
JDK Java 17 프레임워크 Spring Boot 3.4.1 · MyBatis DB MariaDB WAS Tomcat 10

상시모니터링시스템 · 감사정보시스템

유지보수
MonitoringWare · Audit · 2026.04 – 현재 · 고객사 3곳 담당

시나리오별로 정해진 점검 기준에 따라 데이터를 추출하고, 감사 업무에 필요한 정보를 수집·조회하는 두 시스템의 유지보수를 수행했습니다.

  • 기능 개선 — 점검 시나리오의 데이터 추출기준 수정, 알림 API 연동

개인 프로젝트

Expense Tracker · 개인 가계부 웹 애플리케이션

개요

고정지출·수입·계좌를 등록하고 다가오는 결제를 집계하는 가계부입니다. 업무에서 익힌 사내 시스템의 구조 — 공통코드, 논리삭제, 요청 로그, 권한별 메뉴 — 를 직접 설계해보는 것이 목적이었습니다.

github.com/LabSH/EXPENSE_TRACKER

기여한 부분
공통코드 기반 분류 관리 카테고리·지출주기·권한·로그레벨을 코드그룹/코드 두 테이블로 관리하고, 전역 모델 어드바이스로 모든 화면에 주입해 화면마다 조회 코드를 중복 작성하지 않도록 했습니다.
Facade 계층으로 트랜잭션 경계 정리 여러 도메인 서비스를 조합하는 화면 단위 호출을 Facade로 분리하고, 고정지출 논리삭제와 첨부파일 논리삭제를 한 트랜잭션으로 묶어 파일만 남는 상태를 막았습니다.
요청 로그 인터셉터 모든 요청의 처리시간·상태코드·사용자·클라이언트 IP·예외를 로그 테이블에 적재하고, 상태코드에 따라 INFO/WARNING/ERROR 레벨을 부여했습니다.
결정 기록(ADR) 유지 권한별 메뉴 노출 방식, 모달 backdrop 클릭 정책처럼 되돌아보기 쉬운 판단은 이유와 대안을 함께 남겼습니다. 등록·수정 모달은 실수 클릭으로 입력이 날아가지 않게 backdrop 클릭으로 닫히지 않습니다.

트러블 슈팅

상황 · 해결 · 알게 된 점

Ajax 오류 응답에 내부 정보가 섞여 나감

상황 잘못된 JPQL이나 제약조건 위반이 발생하면 예외 메시지가 그대로 클라이언트 응답에 실려, SQL과 예외 클래스명이 노출됐습니다. 해결 전역 예외 핸들러에서 클라이언트로 내보낼 문구를 직접 작성한 BusinessException과 Bean Validation 메시지로 제한하고, 나머지는 일반 문구로 치환해 상세는 서버 로그에만 남겼습니다. 알게 된 점 핸들러 범위를 좁히는 일이 함께 필요했습니다. 뷰를 반환하는 핸들러의 예외는 원본을 다시 던져 기본 오류 페이지로 넘기고, 인증·인가 예외도 다시 던져 Security 필터가 401/403으로 처리하게 뒀습니다. 그러지 않으면 모든 오류가 500 JSON으로 바뀝니다.

예외가 발생한 요청이 로그에 정상(200)으로 남음

상황 전역 예외 핸들러가 예외를 처리하고 나면 인터셉터로 넘어오는 예외 인자가 null이라, 실패한 요청이 로그 테이블에 INFO·200으로 기록됐습니다. 해결 DispatcherServlet이 request attribute에 보존하는 원본 예외를 읽어 복원하고, 예외가 있으면 상태코드를 500으로 보정한 뒤 레벨을 판정했습니다. 알게 된 점 로그를 남기는 코드가 실패해 요청 자체를 깨뜨리면 안 되므로, 적재 로직 전체를 감싸 경고 로그만 남기고 통과시켰습니다.

개발 중 자동 재시작 후 ClassNotFoundException

상황 Controller 안에 중첩 선언한 DTO record가 DevTools 재시작 뒤 로드되지 않아 클래스를 찾지 못했습니다. 해결 DTO record를 별도 파일로 분리하고, 같은 실수가 반복되지 않도록 운영 문서에 규칙으로 적어뒀습니다.
